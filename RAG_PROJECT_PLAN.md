## 2. Architecture decisions (the "why", for `design-and-evaluation.md`)

These are pre-decided so Claude Code builds the right thing the first time. The rationale below is also what feeds the design doc.

**Language / runtime:** Python 3.11. Stable, best LangChain + sentence-transformers support.

**Orchestration:** **LangChain** (required by the brief). Used for loaders, splitters, the Chroma vector store wrapper, the Groq chat model, and the retrieval chain.

**LLM (generation):** **Groq**, `llama-3.3-70b-versatile`, via `langchain-groq`. Chosen for free tier, GPT-4o-class quality, and very low latency (helps the latency metric). Fallback model `llama-3.1-8b-instant` (higher daily request ceiling) configurable via env. Temperature **0** for determinism/reproducibility.

**Embeddings:** **Local HuggingFace** `BAAI/bge-small-en-v1.5` via `langchain-huggingface` (`HuggingFaceEmbeddings`). Chosen because it is: free, **needs no API key**, **has no rate limit** (critical during bulk ingestion and eval), deterministic, small (~130MB) so it deploys cheaply, and strong on retrieval benchmarks for its size. This is preferred over the HF Inference API free tier, which is rate-limited and network-dependent.

**Vector store:** **Chroma** (`langchain-chroma`), persisted to `data/chroma/`. Lightweight, local, zero external service. On a fresh container the app **rebuilds the index at startup if the persist dir is empty**, so deployment never depends on committing binary index files.

**Chunking:** `MarkdownHeaderTextSplitter` → `RecursiveCharacterTextSplitter`. Header-aware splitting keeps each chunk tied to its document **and section**, which makes citations precise (cite *doc title + section*). Defaults: ~1,100 chars, 150 overlap (deterministic). These are the ablation knobs.

**Retrieval:** Top-k similarity (default **k=5**), fetching `k_fetch=15` candidates first. **Optional cross-encoder re-ranker** (`cross-encoder/ms-marco-MiniLM-L-6-v2`, local, free) re-orders the 15 down to 5 — toggled by env var, and used as an ablation.

**Guardrails:**
1. **Out-of-corpus refusal** — a retrieval-score gate (if best similarity is below threshold, refuse) **plus** a system-prompt instruction to answer only from provided context. Refusal text: *"I can only answer questions about Zidipay's policies and procedures."*
2. **Length limit** — `max_tokens` cap + an instruction to be concise.
3. **Always cite** — the answer must list the source doc title + section for every claim; the API returns structured citations with snippets and links.

**Web framework:** **Flask** (not Streamlit). The rubric explicitly requires three distinct routes — a chat UI (`/`), a JSON POST API (`/chat`), and a JSON health check (`/health`). Flask delivers all three cleanly with a tiny HTML/JS frontend; Streamlit does not give clean REST endpoints.

**Deployment:** **Hugging Face Spaces (Docker SDK)** — free, no project cap (Render's free tier is now 1 project, and you already have one), ties in with HF. Deploy is git-push based and CI-friendly. Render (Docker) is the documented fallback if you free up your slot.

**Reproducibility:** Pinned `requirements.txt`; `.env.example`; seeds set in `rag/config.py` (`PYTHONHASHSEED`, `random.seed`, `numpy.seed`); deterministic chunking params; `temperature=0`; eval sampling seeded.

## 3. Evaluation design (feeds `design-and-evaluation.md`)

**Eval set:** 20 questions in `eval/eval_set.json`, each with: `id`, `question`, `gold_answer` (short), `expected_source` (doc + section), `topic`. Topics span PTO, security, expense, remote/hybrid work, public holidays, AML/KYC, travel, onboarding/offboarding, data privacy, whistleblowing. **Plus 4 out-of-corpus questions** (e.g. "What is Zidipay's share price?", "How do I cook pasta?") to test the refusal guardrail.

**Information-quality metrics (required):**
- **Groundedness** — % of answers fully supported by the retrieved context, judged by an LLM-as-judge (Groq, temperature 0) that sees the answer + the retrieved chunks and returns supported / not-supported with a reason.
- **Citation accuracy** — % of answers whose cited sources actually contain the supporting passage. Computed two ways and reported: (a) LLM judge, (b) deterministic check that the cited doc/section is among the retrieved chunks that contain the answer terms.

**Optional quality metric:** Exact/partial match vs `gold_answer` (token-overlap / substring).

**System metric (required):** **Latency p50 / p95** over the in-corpus queries (request → answer), reported in ms. Run twice (cold vs warm) and report warm.

**Ablations (optional, included):** Sweep **k ∈ {3, 5, 8}** and **chunk size ∈ {700, 1100, 1500}** and **rerank on/off**; output a comparison table of groundedness + latency to `eval/results/ablations.md`.

**Outputs:** `eval/results/eval_results.json` (per-question detail) and `eval/results/summary.md` (headline numbers + ablation table) — both committed so the grader sees them without running anything.

## 4. Lane B — Your manual runbook (step by step)

### Step 1 — Get a Groq API key (do this first; Claude Code needs it to run/eval locally)
1. Go to **console.groq.com**, sign up with Google or GitHub (no credit card).
2. Left nav → **API Keys** → **Create API Key** → copy it (shown once).
3. Keep it for `.env` locally and as a GitHub/HF secret later.

### Step 2 — (Optional but recommended) Get a Hugging Face token
You only need this for **deploying to HF Spaces** and as the `HF_TOKEN` CI secret. Embeddings download works without it (the model is public).
1. **huggingface.co** → sign up → **Settings → Access Tokens → New token** → role **Write** → copy.

### Step 3 — Run Claude Code
1. In an empty folder, run Claude Code and paste the entire `PROMPT.md` as your first message.
2. Create a local `.env` (Claude Code generates `.env.example`):
   ```
   GROQ_API_KEY=your_key_here
   GROQ_MODEL=llama-3.3-70b-versatile
   EMBEDDING_MODEL=BAAI/bge-small-en-v1.5
   USE_RERANKER=false
   TOP_K=5
   ```
3. Let it build, then locally: create venv → `pip install -r requirements.txt` → `python run_ingest.py` → `python app.py` → open `http://localhost:5000`. Confirm chat, citations, `/health`, and `python eval/run_eval.py` all work before deploying.

### Step 4 — Create the GitHub repo & push
1. Create a **public** (or private + invite grader) repo, e.g. `zidipay-policy-rag`.
2. `git init && git add . && git commit -m "Initial RAG app" && git remote add origin … && git push`.
3. Confirm `data/chroma/` is gitignored (index rebuilds on deploy) and `.env` is gitignored.

### Step 5 — Add CI/CD secrets & share with grader
1. Repo → **Settings → Secrets and variables → Actions** → add `GROQ_API_KEY`, and (for deploy) `HF_TOKEN` and `HF_SPACE_ID` (e.g. `yourname/zidipay-policy-rag`).
2. Repo → **Settings → Collaborators** → invite **`quantic-grader`**. (Do this even if the repo is public — the brief requires it.)
3. Push a small commit / open a PR and confirm the **Actions** tab shows a green run (install + import check + pytest).

### Step 6 — Deploy (Hugging Face Spaces, recommended)
1. huggingface.co → **New Space** → SDK **Docker** → name it → **Public**.
2. Easiest path: in the Space settings, **link the GitHub repo** (or push to the Space's git remote). The committed `Dockerfile` builds it.
3. Space → **Settings → Variables and secrets** → add `GROQ_API_KEY` (and any others).
4. Wait for build → you get a public URL like `https://huggingface.co/spaces/yourname/zidipay-policy-rag`. Put it in `deployed.md` and commit.
5. *CI-triggered deploy (optional flourish for the rubric):* the generated `ci.yml` has a `deploy` job that, on green `main`, pushes to the Space using `HF_TOKEN`/`HF_SPACE_ID`. Enable it once secrets are set.

*Fallback — Render:* if you prefer Render, pause or delete your existing free project first (free tier = 1 project), then New → Web Service → connect repo → Docker → add `GROQ_API_KEY` env var. Note the 15-min spin-down → warm it up right before recording.

### Step 7 — Record the demo & submit
1. Record with Loom or OBS, 5–10 min, **you on camera + show your government ID** (rubric requirement, even solo).
2. Follow the demo script in §5.
3. Assemble a **single PDF** with two links: (1) the GitHub repo, (2) the demo video. Submit.

## 6. Risk notes / gotchas

- **Groq free limits** (~1,000 req/day, 30 RPM): the eval harness adds a small sleep between calls and uses the LLM judge sparingly so a full eval run stays under the cap. If you hit limits, switch `GROQ_MODEL` to `llama-3.1-8b-instant` (higher ceiling).
- **First load downloads the embedding + reranker models** (~hundreds of MB). Expect a slow first ingest; subsequent runs are fast. The Dockerfile pre-downloads them at build time so deploy cold-starts are quicker.
- **HF Space sleeps on inactivity** — open the URL a minute before recording so it's warm.
- **Don't commit `.env` or the Chroma DB.** Index rebuilds from `corpus/` on startup.
- **Citations must be real.** The eval's deterministic citation check will catch hallucinated sources — keep the guardrail strict (cite only retrieved chunks).
